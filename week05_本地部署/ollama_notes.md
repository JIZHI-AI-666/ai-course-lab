## 三 安装与排错实录

1. 从 Ollama 官方站下载并检查 macOS 安装脚本，应用安装至 /Applications/Ollama.app。
2. 官方脚本尝试在 /usr/local/bin 创建命令入口时需要管理员密码，因此在已有 PATH 的 /opt/homebrew/bin 创建指向应用内可执行文件的软链接。
3. 启动应用后，用 `ollama --version` 和 `/api/tags` 验证服务。启动初期曾连接失败；稍后应用服务启动，再手动启动会提示端口占用，此时复查接口已正常，无需重复启动。
4. 执行标准下载命令 `ollama pull qwen2.5:0.5b` 时，当前代理 DNS 将下载域名解析到非公网地址，触发下载器限制。实际采用官方 registry 的 manifest 与 blob 下载，逐文件核对 SHA-256 和文件大小，再导入本机模型缓存。没有关闭 TLS 校验，也没有修改全局代理设置。
5. 实测 0.5B 正确回答“1加1等于2”，初次简单问答墙钟约 1.31 秒。当时 `ollama ps` 显示约 483 MB、100% GPU；下面学科实验使用固定参数重新测量，数字不与该简单测试混用。

正常网络环境下的基本操作：

```bash
ollama pull qwen2.5:0.5b
ollama run qwen2.5:0.5b
# 对话输入 /bye 退出
ollama list
ollama ps
curl http://127.0.0.1:11434/api/tags
# 仅在服务未启动时运行：ollama serve
```

本次 Python 使用标准库 urllib，访问本地地址时显式不走代理，与讲义 requests.Session().trust_env=False 的意图一致。超时设置 180 秒；本地读写均使用 UTF-8。

## 四 实验方法

题目原文与预设评价标准见 questions.json，完整回答、参数及耗时见 results/*.json。所有素材均为通用知识或虚构文本，没有真实学生个人信息。

- 三个模型使用相同的用户提示词，各题独立请求，不携带上一题对话。
- temperature=0.2；本地 num_predict=600，云端 max_tokens=600；本地 num_ctx=4096、seed=42。不同模型分词器不同，相同 token 上限不代表相同汉字数。
- 本地每组开始前卸载已加载模型。第 1 题包含冷加载，第 2—5 题为热调用；每组结束后卸载模型，避免两个量级同时占用内存。
- 速度是客户端从请求到完整回答的墙钟时间，不是首 token 延迟；本地另保存 load_duration、eval_count 等原始指标。
- 每题每模型只运行 1 次，不以单次样本推出普遍速度或质量排名；下载时间不计入推理时间。
- 云端按上周设置使用 deepseek-chat。实际计费以服务商账单为准，本次保存 token 用量，没有虚构价格。

## 五 不同量级模型比较

两者同属 Qwen2.5、均为 Q4_K_M，固定相同提示词和本地参数。大小不是唯一变量：不同参数模型的训练差异也可能影响输出。

| 指标 | 0.5B | 1.5B |
|---|---|---|
| 权重主体文件 | 397,807,936 字节 | 986,048,512 字节 |
| 第1题墙钟时间（含冷加载） | 1.11 秒 | 3.01 秒 |
| 第1题服务端加载时间 | 0.54 秒 | 1.29 秒 |
| 第2—5题平均墙钟时间 | 0.87 秒 | 2.25 秒 |
| 第1题后 API 报告的模型运行占用 | 483.6 MB | 1169.4 MB |
| 上下文设置 | 4096 tokens | 4096 tokens |

这里 MB 使用十进制；/api/ps 的 size 是 Ollama 报告的模型运行占用，不是整机内存或进程全部 RSS，Apple 统一内存下也不能把 size 与 size_vram 再相加。表中的热调用平均包含不同长度回答，不能据此单独归因于模型大小。

| 题目 | 0.5B耗时 | 1.5B耗时 | 1.5B相对改善及仍存问题 |
|---|---|---|---|
| 把字句纠错 | 1.11s | 3.01s | 仍把喜欢与读完混为等价，未正确判断原句；关键语法不合格。 |
| 依据材料出阅读题 | 0.23s | 0.96s | 能解释公交耗时更长，未再编造交通事故；仍没有四个选项、答案和出题格式。 |
| 近义词辨析 | 0.98s | 3.09s | 以次数与性质区分再和又，并误判昨天我再去了图书馆为正确；关键语法不合格。 |
| 教学活动设计 | 1.91s | 3.88s | 回到把字句主题，2+3+5=10分钟；却把结构写成把+动词+宾语，存在关键错误，活动步骤较空泛。 |
| 虚构作文反馈与隐私 | 0.36s | 1.06s | 改写较连贯，但缺少优点／问题／修改建议三段反馈，并添加未给定的感受与阅读建议。 |

**判断：这组任务上，质量提升不值得仅为教学答案自动生成而增加内存。** 1.5B 的模型运行占用比 0.5B 多约 686 MB，约为其 2.42 倍；部分内容更贴题，但仍未达到关键检查点。保留 0.5B 用于课程运行演示与可逐项校验的小任务，1.5B 用于对比研究；需要语法准确性的任务采用经教师核验的材料，公开非敏感内容可用云端辅助。敏感材料不能因为云端质量较好就直接上传。该结论只适用于本次5题、单次调用和固定设置，不代表所有1.5B任务都无提升。

## 六 官方文档学习记录中的三条用法

以下是本次整理并可复现的用法；是否属于本人“以前不知道”，需在提交后学习演示时亲自确认。

### 1 用 Modelfile 保存教学助手配置

本目录 Modelfile 以现有 0.5B 为基础，设置 temperature、num_ctx 和 SYSTEM。已实际运行创建命令并检查参数，属于配置派生模型，不是训练或微调，也不代表下载了另一个参数量的模型。

```bash
ollama create chinese-teaching-w5 -f Modelfile
ollama show chinese-teaching-w5 --parameters
ollama run chinese-teaching-w5
```

官方来源：[Modelfile Reference](https://docs.ollama.com/modelfile)。

### 2 原生 API 的生成参数放在 options 中

本次实测的请求结构如下；`stream:false` 返回一个完整 JSON，避免把流式多行响应误当作单个 JSON。

```json
{
  "model": "qwen2.5:0.5b",
  "messages": [{"role":"user","content":"解释把字句，限100字。"}],
  "stream": false,
  "options": {"temperature":0.2,"num_predict":600,"num_ctx":4096},
  "keep_alive":"10m"
}
```

这与云端兼容接口的顶层 `temperature`、`max_tokens` 写法不同；降低 temperature 不保证事实正确，输出上限过短会造成截断。来源：[Chat API](https://docs.ollama.com/api/chat)。

### 3 主动管理模型常驻时间并查看占用

`ollama list` 看磁盘上有什么，`ollama ps` 看内存中运行什么。`keep_alive` 可以控制常驻；实验通过空 generate 请求与 `keep_alive:0` 卸载模型，也可用 `ollama stop qwen2.5:0.5b`。本次脚本实际验证了卸载、冷加载与读取 `/api/ps`。

来源：[CLI](https://docs.ollama.com/cli)、[FAQ](https://docs.ollama.com/faq)、[运行模型 API](https://docs.ollama.com/api/ps)。

## 七 无网乡村学校的部署准备与复盘

如果把这台 16 GiB 的 M4 电脑带到无网教室，我会在有网时先准备匹配系统架构的 Ollama 安装包、已验证的模型权重及配置、许可证、Python 安装包（目标机未安装时）、本作业脚本与一组公开或虚构测试题。不能只带安装器，到现场才运行 pull；模型和依赖也必须提前备齐。本脚本只用标准库，可减少离线依赖准备。

模型先带 0.5B 作为启动演示和简单格式任务的保底；教学准确性不能以“能运行”代替验收。第二个模型是否值得使用，应依据同题质量与占用比较决定。16 GiB 预算可先预留约 6 GiB 给系统和教学软件、约 2 GiB 作余量，剩余约 8 GiB 作为推理试运行预算；这是部署规划而非系统实测，不把内存全部分给模型。关闭不用的模型、限制上下文与并发，再观察实际占用和系统响应。

迁移优先在相同 Ollama 版本及目标系统测试。若使用 GGUF 导入，应同时准备与模型匹配的模板和配置，通过 Modelfile 的 FROM 引入本地 GGUF 后 `ollama create`，再用固定题目核验；不能假设任意 GGUF 加一个文件名就会有正确对话模板。也可以在同版本测试完整模型缓存迁移，macOS 默认位于 `~/.ollama/models`，必须包括 manifests 和 blobs，并在复制前后做完整性检查。参见 [官方导入说明](https://docs.ollama.com/import) 与 [存储位置说明](https://docs.ollama.com/faq)。

出发前应断网完成一次“重启服务—查看模型—Python 问答—保存结果”的演练；本次只完成本地接口实测，尚未实际关闭整机网络，不能称为已完成断网验收。课堂预案准备纸质题目与教师核验答案，模型失败时仍可上课。含姓名的作文与成绩保存在受控本机目录，不随公开仓库分发；服务保持本机监听，不随意开放给全校网络。

本节为扩展部署方案。所提供第五次课讲义没有指定文章阅读交付要求，不将其他材料中的阅读任务计入本次验收清单。

## 八 术语 隐私与成本边界

量化是降低权重数值表示精度，以减小存储与内存需求，可能损失质量；速度效果还依赖硬件和实现。MCP 是连接外部工具与数据的协议，不负责把权重压进小内存。

学生作文原件、成绩评语、姓名学号、联系方式、未公开试卷与内部研究材料，不应直接发到云端。必要时先用代号替换身份信息，去除联系方式、间接可识别经历等，只发送完成任务需要的最少内容；映射表留在本机。脱敏还要遵守学校要求，删除姓名并不自动等于没有隐私风险。

调用少且要求质量时，云端通常省去硬件和维护投入；高频、要求离线或隐私时，本地更有价值。本地没有按 token 的 API 账单，但仍有电费、存储、内存、安装维护和人工纠错成本；不能只按响应时间判断“划算”。

## 九 课后思考题

1. 本机 16 GiB。按讲义可以考虑 4B Q4，但本次选择 0.5B 与 1.5B，尚未验证更大模型。8B 及以上会进一步挤压系统和上下文缓存空间；不是模型能装到磁盘就能流畅运行。
2. 批改含姓名的 40 篇作文，优先本地处理并由教师复核。若必须上云，先确认学校允许，再去除直接与间接身份信息、保留必要片段，不能把整份原始名单或作文批量上传。
3. 本地输出质量还受量化精度、上下文是否够用、提示词是否明确、采样参数、输出长度是否截断、训练与指令对齐情况影响。先核对事实依据和完整性，不能把所有错误归结为“模型小”。
